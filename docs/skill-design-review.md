# VAPA Skills 设计审查

审查日期：2026-10-15。初审基线：`2e2eb04`；提交前同步到主分支 `1351ee5`，纳入新增 `vapa-design` 与最新父子任务协议。范围：`skills/` 的六个发布入口、三个 shell 后端、标签配置器、模板、原有测试，以及 README 与框架的能力声明。本地 `.agents/`、`.claude/` 和安装锁文件属于已有未提交内容，不作为发布源，也未修改。

## 结论

**保留六个 Skills 的总体分工，以 `v0.1-draft` 早期公开预览对外介绍。** 这套设计最有价值的部分，是把“提案是否值得做”和“实现是否符合承诺”分别交给不同阶段判断，并让执行上下文留在项目中。

原版本还不足以支撑“装上就能在所有 Agent 和 GitHub 仓库中完整运行”的承诺。主要缺口在脚本失败处理、真实副作用说明、宿主适配和验证证据。本轮修复可确定的错误，同步产品介绍；保留组织写入端到端验收、跨宿主兼容性矩阵等后续工作。

本报告是当前会话的源码审查和本地验证记录，未经过另一个独立 Agent 审核，也未对真实组织执行初始化或创建测试提案。

## 值得保留的设计

1. **按决策与交接边界拆分，而不是按工具拆分。** `init → proposal → design → review → exec → audit` 对应不同输入和结果，使用者容易判断下一步该用什么。新增的设计阶段把方案确认放在正式评审之前。
2. **提案评审只读。** `vapa-review` 的后端只有上下文读取入口；输出建议不等于批准，没有把顾问角色和治理权限混在一起。
3. **协议与确定性操作分开。** Skills 承担判断与流程，脚本承担 GitHub 操作，`references/` 承担模板。无需为了“更产品化”另加一个运行平台。
4. **执行有持久交接记录。** `.vapa/` 中的问题摘要、来源、计划、日志、测试和 PR 草稿支持跨人、跨会话继续工作。
5. **审计保留三种不同结果。** 可以交给人评审、Agent 能自行返工、需要人决定方向，这三种情况有不同后续动作。

## 已发现并修复的问题

### P1 · 组织字段类型冲突会触发删除重建

原 `ensure_issue_field` 发现同名字段不是 `single_select` 时，会直接调用组织级 DELETE，再创建新字段。Skill 却声称不会创建或删除组织字段。已有引用和历史值可能受到影响，影响范围超出单个仓库。

**修改：** 不再删除字段；类型冲突立即失败，要求另行制定迁移方案。读取失败、JSON 解析失败及更新失败也中止执行，不能继续进入后续初始化并宣告成功。文档说明 `--init-fields` 的组织级作用范围。

**证据：** [字段处理函数](../skills/vapa-init/scripts/vapa-init.sh#L152)；[真实 CLI 的替身测试](../tests/test-vapa-init.sh)，覆盖类型冲突、查询失败、无效 JSON、PATCH 失败，验证不发生删除、创建或后续仓库写入。

### P1 · 完整 Issue URL 的仓库身份被丢弃

原 `vapa-review` 只从 URL 提取编号，再把它与当前仓库组合。审查 `example/other#42` 时，可能读取当前仓库中的 `#42`，并基于错误上下文输出评审。

**复现：** 给后端传入 `https://github.com/example/other/issues/42` 与 `--repo insentek/VAPA`，原实现实际请求 `issue view 42 --repo insentek/VAPA`，退出码为 0。

**修改：** 完整 URL 同时决定仓库与编号；与显式 `--repo` 或 `VAPA_REPO` 冲突时拒绝执行。校验正整数编号、完整 GitHub URL、大小写等情况。仍保持只读。

**证据：** [上下文解析](../skills/vapa-review/scripts/vapa-review.sh#L78)；[回归测试](../tests/test-vapa-review.sh)。

### P1 · 编号查询失败被当成“仓库没有提案”

原编号函数吞掉 `gh issue list` 的错误，接着返回 `0001`。权限或网络失败可能变成错误编号，并继续创建提案。

**复现：** 用退出码 1 的 `gh` 替身调用原 `get_next_vep_number`，得到 `0001`，函数退出码为 0。

**修改：** 查询失败时返回非零退出码；创建函数显式传递错误，禁止继续到 POST。编号分配发生在草稿提交时，Skill 中的“批准后编号”也已更正。

**证据：** [编号查询与创建](../skills/vapa-proposal/scripts/vapa-proposal.sh#L45)；[失败后不调用写 API 的测试](../tests/test-vapa-proposal.sh)。

### P1 · 初始化会截断含点号的仓库名

原 origin 正则在 `.` 前停止，`owner/project.v2.git` 会被识别为 `owner/project`，后续写入可能指向错误仓库。

**修改：** 保留完整仓库名，只剥离末尾 `.git`。替身测试通过实际 CLI 和模拟 origin，验证目标仍为 `owner/project.v2`。

**证据：** [origin 检测](../skills/vapa-init/scripts/vapa-init.sh#L47)；[初始化回归测试](../tests/test-vapa-init.sh)。

### P2 · Reset 按空格拆开标签名

原 `for name in $vapa_names` 把 `status: draft` 拆成两个名字，无法按声明清理当前标签。旧标签的循环存在同样问题。

**修改：** 按行读取并保持标签完整。测试核对实际发出的删除端点包含 `status%3A%20draft`，并在模拟删除失败时停止。

**证据：** [Reset 逻辑](../skills/vapa-init/scripts/vapa-init.sh#L321)；[初始化回归测试](../tests/test-vapa-init.sh)。

### P2 · 触发条件、规模门槛和审计独立性不一致

- `vapa-exec` 的 “fix / refine proposal” 容易与提案完善混淆。已把入口限定到执行计划、实现与实现返工，提案撰写和评审分别交给对应 Skill。
- 框架准入清单要求 M 及以上全部拆分，执行策略却允许 M 使用分离角色。已统一为：M 记录拆解决策与策略，L / XL 先拆为经批准拆分方案覆盖的 S 子 Issue。（2026-10-21 注：该规则已被当前执行协议取代，执行策略不再由 Size 决定，以 [vapa-exec](../skills/vapa-exec/SKILL.md) 为准。）
- 同一会话切换角色不产生独立验证。已要求审计记录 base/head 或未提交 diff、审计者 / 会话、是否参与实现；同会话明确标为自审。
- `vapa-audit` 仍将已经存在的 `vapa-review` 写成未来能力，已修正。
- 初始化说明把六个字段写成七个，并遗漏模板直接提交默认分支的行为，已修正。

**证据：** [执行协议](../skills/vapa-exec/SKILL.md)、[审计协议](../skills/vapa-audit/SKILL.md)、[初始化协议](../skills/vapa-init/SKILL.md)、[完整框架](framework.md)。这些属于协议一致性修订，不代表所有 Agent 都已按新协议完成行为验收。

## 仍存在的设计限制

### P2 · VEP 编号不是原子分配

`max + 1` 没有并发锁，查询最多覆盖 1,000 条匹配记录。两个同时提交的提案可能使用相同展示编号。

**本轮处理：** 在 Skill 和 README 明确限制，以 GitHub Issue 编号 / URL 作为身份，不把展示编号宣称为唯一 ID。

**后续选择：** 在需要强唯一编号时，改为创建 Issue 后派生编号，或引入单点分配；这是编号协议变更，应单独设计与迁移。本轮没有宣称解决并发问题。

### Codex 包兼容已修复；跨宿主端到端仍需验证

初审时，三个脚本型 Skills 含 Claude 的路径占位符、工具配置与 `disable-model-invocation` 字段；当时 Codex 规范校验为两项通过、三项失败。

**后续修复：** 应用户要求，通用 `SKILL.md` 仅保留标准元数据，移除 Claude 专用工具白名单和路径变量；命令使用实际安装目录、带引号的路径及显式 Bash。三个脚本型 Skill 与主分支新增的 `vapa-design` 分别配置 `agents/openai.yaml`，以 `policy.allow_implicit_invocation: false` 保留 Codex 中的显式调用策略，配置依据为 [OpenAI Docs](https://learn.chatgpt.com/docs/build-skills#optional-metadata)。

**调用行为的差异：** Claude 专有的自动发现禁用字段已从通用入口移除，其他宿主使用其自身发现机制；正文仍要求用户明确请求该工作流，初始化和提交仍保留写入前的预览确认。Codex 的显式调用限制由侧边配置控制。

**当前验证结果：** 六个 Skill 均通过 Codex 自带 `quick_validate.py`、项目包检查和实际 Codex `0.162.0-alpha.17.2` 的 `skills/list` 加载。测试复制完整 Skill 到带空格路径的临时 `.agents/skills` 中，验证全部被发现、启用；四个显式调用入口还检查显示名称与 `$skill` 默认请求。没有启动模型执行，也没有写入 GitHub。可用 `node tests/test-codex-loading.cjs` 复现。

**尚需验证：** 在试用组织仓库逐宿主验证提案确认、真实 GitHub 写入和执行 / 审计交接；包格式和加载通过不能推断为完整工作流端到端通过。

### P2 · 初始化预检对 API 错误的诊断仍不充分

只读检查中的部分 `gh api ... || true` 会把缺权限、API 不支持和配置不存在都表现为缺失。字段写入路径现已在查询失败时停止，但“检测报告是否精确区分原因”仍需完善。

**后续建议：** 返回结构化检测结果，区分 present、missing、forbidden、unsupported 与 request-failed，并验证个人仓库、无组织管理员权限和受保护默认分支等场景。

### P3 · 小任务的流程成本与协议维护成本

执行入口仍要求完整的工作区产物；三个地方维护近似提案模板。对小任务可能偏重，模板也可能漂移。

**建议：** 保留现有职责边界，先收集真实任务中的重复劳动，再设计精简记录模式；需要简化的是阶段内的文书负担。暂不新增总控 Skill、自动审批或自动积分。

**2026-10-21 跟进：** 执行协议已合并来源、准入与代码库调研记录到 brief 和计划，日志不再复述 Git 历史，记录深度随风险调整。
